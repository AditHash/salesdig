# V2 baseline and Seller Company Profile

The current app is React/Vite and Express/TypeScript. PostgreSQL holds users, workspaces, analysis runs, reports, chat, activity, and pgvector embeddings. `backend/src/config/postgres.ts` creates the V1 schema at startup; `backend/migrations/` adds tracked, additive migrations. Account research and opportunity matching use PostgreSQL-backed queues with short leases and polling from the account page. Workmates is seeded as a regular workspace with default settings.

Authentication loads the user and workspace from PostgreSQL for each request. The only current roles are `admin` and `user`; V2 Seller Company Profile edits map to `admin`, while members can read. Future Owner, Sales Manager, Sales Rep, and Viewer roles remain for later milestones. Profile data extends `workspaces`; name and description stay in existing `settings` JSONB for V1 compatibility. No legacy report or run is linked to a new target account. Existing report ownership and workspace filters remain in place, including report export and chat retrieval; no affected workspace leak was demonstrated in the baseline review.

Baseline commands: `cd backend && npm run build`, `cd frontend && npm run build`. There was no test or lint script before V2. `cd backend && TEST_DATABASE_URL=... npm test` now runs the HTTP authorization and profile integration checks. A dedicated database ending `_test` with pgvector is required. Tests create and remove their own fixtures. The test database must stay isolated from shared Neon data. The local checks covered login, profile read/update, legacy report list/detail/run, PDF generation, chat history, invalid research submission without a run, cross-workspace denial, and a Chromium walkthrough of profile validation, completion, and reload persistence. Paid Gemini research and chat answers were not called.

The migration preserves existing workspace settings and reports. New profile columns start empty with `not_started` status and version `0`. Company name, website, and description are required only when marking onboarding complete. Existing V1 features stay accessible during onboarding. A profile edit increments `profile_version`; an existing V1 company-settings edit also increments it when name or description changes. The frontend saves unrelated preferences through a partial update that retains the current profile fields.

Step 2 adds `target_accounts` with workspace and owner scoping, plus optional account references on V1 runs and reports. Exact active name/domain duplicates are rejected; shared domains with distinct names are allowed. Existing reports remain unlinked until their owner explicitly links one to a matching-domain account. Research from an account uses the existing synchronous orchestrator; only one active run is allowed per account. Reports remain subject to V1 owner/admin access. Account deletion is archive-only, preserving report history.

Step 3 adds `005_research_evidence.sql`: tenant-bound source and claim records, durable run stages, retry metadata, resource usage, and report status fields. Account research now returns a queued run; an API-process worker claims it with a PostgreSQL lease and resumes queued jobs after restart. Source fetching is capped and rejects private destinations, model claims require a same-run source excerpt, and incomplete runs retain labelled partial evidence. Checks against an isolated `_test` database covered queueing, cross-workspace evidence denial, partial results, retry reuse without duplicate sources or reports, V2 PDF export, and protection against regenerating an evidence-backed report through V1. Live Gemini/search calls were not used.

Step 4 adds `006_target_intelligence.sql`. It projects a completed run's validated claims into tenant-bound technologies, people, buying signals, and gap hypotheses. Every projection retains its claim ID; the account endpoint checks workspace ownership before returning it. The extraction contract requires sourced people, classifies job-post evidence as likely technology usage, deduplicates signals by normalized event fingerprint, and rejects gaps based on missing public information. The account page has Overview, Tech DNA, Stakeholders, Buying signals, Potential gaps, and Sources states. Isolated checks covered the migration, cross-workspace intelligence denial, and these validation rules; live Gemini extraction was not invoked.

Step 5 adds `007_opportunity_matching.sql`. It stores an immutable matching snapshot for a completed account research run, its approved seller-offering versions, evidence-linked opportunities, and component-level score data. The application calculates Sales Potential from explicit components: offering fit, business pain, buying signals, technology compatibility, financial capacity, decision-maker accessibility, and strategic timing. Missing components are excluded from the normalized score and shown through evidence coverage; the result is a prioritization rubric rather than a purchase probability. The account page displays supported need or discovery hypothesis, evidence, why-now context, entry action, uncertainties, and a transparent no-match result. Isolated PostgreSQL checks cover approved-offering selection, workspace denial, same-input determinism, bounds, and missing-data behavior. Provider calls are not used for matching.

Startup first ensures the V1 tables and pgvector extension exist, then applies numbered SQL files from `backend/migrations/` under a transaction and advisory lock. Keep that directory with `dist/` when packaging the backend. `schema_migrations` records applied files. If a migration fails, the transaction rolls back and startup fails; correct the problem and restart. Prefer a forward fix and restore from a backup if needed. Dropping the new columns would discard profile data, so there is no data-preserving down migration.

Step 6 adds `008_account_chat.sql` and `009_sales_preparation.sql`. Existing global chat sessions/messages remain readable; per-account sessions are scoped by workspace, user and account. Account mode loads at most 20 cited claims, 40 excerpts, 10 current offering matches and 10 approved offerings from the latest completed research snapshot, plus bounded notes. These limits are disclosed in model context; absence from the bounded context does not imply absence in the account. Historical chat is conversational continuity, not evidence. The provider receives policy separately from untrusted context, unsupported claim citation IDs are rejected, and supplied source references are saved for inspection. No account query retrieves unrelated V1 report digests. Global report retrieval and follow-up query rewriting remain compatible. Empty account evidence skips the provider.

Sales preparation uses deterministic `evidence-template-v1` templates for seven draft kinds, without paid generation. Creation requires a supported opportunity and its still-approved, active, unchanged seller offering version. Drafts retain the selected research/set/offering versions and supporting claims, source excerpts, retrieval/publication dates, and uncertainty. Drafts are private to their author; edits require the current revision and retain immutable source snapshots and revision history. User edits remain unverified. Archived accounts retain drafts but cannot create/edit them. Cold-email drafts are never sent.

The account page links preparation and chat, polls queued offering matching, and exports available intelligence and the author's drafts as provenance-preserving JSON. Opportunity display/export uses the saved offering-version name. The Analysis dashboard loads real workspace totals. Existing report PDF export, global chat history, and V1 ownership rules remain unchanged. Account history returns its latest 100 messages; draft listing returns the author's latest 50 drafts. There is no separate workspace-switch UI; user/workspace/account changes remount private account/chat state.
